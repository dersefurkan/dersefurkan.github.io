Agents

3. Unchecked tool argument

Description. The tool runs the argument the model produced. It does not compare the argument to the caller. A user_id, a path, a tenant, or an amount is whatever the model wrote. This is the confused deputy: the tool's authority is the server's, and the choice was the text's.

Why it matters. The model can be "helpful" and the tool is still wrong. Filtering the prompt does not fix a tool that never looks at the session.

Detection hints.

  • Open the tool implementation. Find the parameter that names an object. Find the line that binds

    • it to the session. If that line is missing, the class is present whether or not a model is attached.

  • Call the tool directly, as the server would, with the caller's session and another object's id.
  • Invariant: the other object is unchanged, and the response is a denial.

Example test. Session is tenant A. Call the read tool with tenant B's id, the way the agent would. Assert denial. Repeat through the chat only after the direct call is understood. The chat run shows whether the model will produce the bad argument. The direct call shows whether the tool would honor it.

Field note

The tool runs the argument the model produced and does not compare it with the caller. A user id, path, tenant, or amount is whatever the model wrote. This is a confused deputy: the tool's authority is the server's, and the choice was text. Prompt filtering does not fix a handler that never reads the session.

Detection hint. In the tool implementation, find the parameter that names an object. If that value is the lookup or mutation key and is not replaced by, or intersected with, the authenticated session before the action, the class is present whether or not a model is attached.

Reference: https://genai.owasp.org/llmrisk/llm062025-excessive-agency/ — LLM06:2025 Excessive Agency says to run the extension in that user's context and to enforce authorization in the downstream system, not in the model.
