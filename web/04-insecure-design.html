4. Insecure design

Description. The steps are implemented as specified, and the specification allows the wrong party or the wrong order. A refund before a payment. A ship before a capture. A limit that resets because the counter is the client's. This is not an implementation typo. The rule was never a rule.

Why it matters. Fixes that only escape output do not touch it. The state machine is the bug. Two honest requests, in an order the business does not mean, move the value.

Detection hints.

  • Write the legal order of the scoped flow as states. Any request that skips a state is the test.
  • Ask who must agree. If the server does not store that agreement, the client can skip it.
  • A numeric limit that the client sends is the client's number.
  • Invariant: the illegal order does not change the ledger, the shipment, or the role.

Example test. Create an unpaid order. Call the ship endpoint. Assert the order is still unpaid and no shipment record exists.

Public references.

  • OWASP Top 10 2021 — A04 Insecure Design

Field note

Insecure design is a missing or ineffective control, not an implementation typo. The steps match the specification, but the specification lets the wrong party or the wrong order move value: a refund before payment, a shipment before capture, or a limit the client supplies. Escaping output does not fix it. The state machine is the control.

Detection hint. Write the legal checkout order as server-owned states (priced, paid, captured, shipped). Flag a transition the server accepts when a required prior state, or a required agreement, is not stored on the server. A quantity, price, or reset counter sent by the client is the client's number, not a limit. The illegal order must not change the ledger, the shipment, or the role.

OWASP Top 10:2021 A04 separates this from insecure implementation. A correct implementation cannot add controls that were never designed. Threat modeling of business flows belongs in the design.
